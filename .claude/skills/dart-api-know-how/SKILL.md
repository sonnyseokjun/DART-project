# DART OpenAPI Know-how

DART OpenAPI를 다루는 모든 작업에서 지켜야 할 절차와, 문서만 봐서는 모르는 함정 지식.

## 기본 규칙

- 모든 호출은 `disclosures/dart.py`의 함수를 통한다. 새 엔드포인트가 필요하면 dart.py에 추가하고, 뷰·태스크에서 requests를 직접 쓰지 않는다
- 인증키는 `settings.DART_API_KEY`(.env)에서만 읽는다 — 코드·산출물에 키 값을 남기지 않는다
- **뷰(웹 요청)에서 DART를 호출하지 않는다** — 수집 파이프라인만 호출한다 (프로젝트 핵심 설계 원칙)

## 응답 형태의 함정 (중요)

| 엔드포인트 | 정상 응답 | 오류 응답 |
|-----------|----------|----------|
| corpCode.xml | ZIP 바이너리 | XML (`<status>`, `<message>`) |
| document.xml | ZIP 바이너리 (내부에 XML) | XML |
| list.json | JSON | JSON (`status` 필드) |

- 같은 엔드포인트가 성공/실패에 따라 다른 Content-Type을 반환하므로, ZIP 시그니처(`PK`) 또는 status 필드로 분기한다 (dart.py에 구현됨)
- `list.json`의 status `000`=정상, **`013`=조회 결과 없음(오류 아님, 빈 목록으로 취급)**. 그 외는 `DartApiError`
- corpCode.xml에는 비상장 법인이 다수 포함 — `stock_code` 유무로 상장사를 필터링한다

### document.xml 원문의 인코딩 (실측)

**원문 인코딩은 UTF-8이다.** `dart.fetch_document`의 `decode('utf-8')`이 옳다.

함정: **거래소공시류 HTML 원문은 헤더에 `charset=euc-kr`로 잘못 선언한다.** 실제 바이트는 UTF-8이므로, 선언된 charset을 믿고 EUC-KR/CP949로 디코딩하면 한글이 전부 깨진다. `resp.encoding`이나 `<meta charset>`을 따라가지 말고 UTF-8로 고정할 것.

### document.xml 원문의 두 가지 포맷

| 공시유형 | 원문 포맷 | 판정 |
|---|---|---|
| 거래소공시·공정위공시 등 | `<html>` HTML 문서 | `dart.is_dart_xml()` False |
| 정기공시·주요사항보고·발행공시·지분공시 | `<DOCUMENT>` DART 전용 XML (dart4.xsd) | True |

- 두 포맷 모두 `dart.preprocess_document()`가 처리한다(스크립트·스타일 제거 → 태그 제거 → 공백 정규화)
- DART XML의 표 셀은 `TD`/`TH` 외에 **`TU`(단위값)·`TE`(추출값)** 도 쓴다. 셀 종료를 구분자로 치환하지 않으면 `1,234`와 `5,678`이 `1,2345,678`로 붙어 숫자 대조가 불가능해진다
- 태그 사이의 줄바꿈은 들여쓰기일 뿐이다. 먼저 모든 공백을 눌러 없앤 뒤 태그로만 줄 구조를 복원해야 표 한 행이 여러 줄로 쪼개지지 않는다

### 대형 서식은 섹션을 골라 써야 한다 (실측 토큰, `o200k_base`)

| 유형 | 표본 | 원문 | 전체 정제 | 섹션 추출 |
|---|---|---|---|---|
| 거래소공시 | 20260428800513 | 12,705자 | 1,110토큰 | — |
| 공정위공시 | 20260430001606 | 5,822자 | 413토큰 | — |
| 주요사항보고 | 20260624000420 | 36,478자 | 5,827토큰 | — |
| 지분공시(대량보유) | 20260504000362 | 146,187자 | 8,731토큰 | — |
| 정기공시(분기보고서) | 20260515002181 | 4,318,370자 | **246,375토큰** | 7,756토큰 |
| 발행공시(증권신고서) | 20260624000511 | 4,157,032자 | **413,650토큰** | 46,273토큰 |

- 정기공시·발행공시는 통짜로 LLM에 넣을 수 없다. `dart.KEY_SECTIONS_BY_TYPE`의 `<SECTION-1>`/`<SECTION-2>` 제목 접두어 화이트리스트로 필요한 절만 뽑는다
- **증권신고서는 제1부(모집·매출) + 제2부(발행인에 관한 사항) 구조이고 제2부가 사업보고서 전체를 반복한다.** 로마 숫자(`I.`, `II.`, `III.`)가 두 부에서 중복되므로 제목 전체로 접두어를 비교해야 구분된다
- 매칭되는 섹션이 하나도 없으면 `extract_key_sections`가 `None`을 반환한다 — 호출자는 원문 전체 정제로 되돌아간다(빈 본문 저장 금지)

## 호출량 규칙

- 일일 한도 약 20,000회(개인 키). 대량 조회는 `corp_code` 없이 날짜 범위로 시장 전체를 받아 로컬 필터링한다 (PLAN.md 12.2 — 기업 수와 호출 수의 분리)
- `page_count` 최대 100. 페이지네이션은 `iter_disclosures()` 사용
- 같은 `rcept_no`의 원문을 두 번 받지 않는다 — `Disclosure.raw_fetched` 확인 후 호출. 원문 확보는 `fetch_documents` 명령 한 경로로만 한다(선별 대상 + 미확보분만 조회)
- **원문은 크다.** 정기공시(분기·사업보고서)·발행공시(증권신고서)는 1건이 4~7MB다. 대량 실행 전에 `--limit`으로 소량 검증할 것

### `list.json` 검색기간 3개월 제한 (실측)

`corp_code` 없이 날짜 범위만으로 조회하면 **검색기간이 3개월로 제한**된다. 이걸 넘기면 빈 결과가 아니라 오류로 떨어진다:

```
DART API 오류 [100] corp_code가 없는 경우 검색기간은 3개월만 가능합니다.
```

- **실측 경계 (end_de=20260726 기준): 89일 통과 / 92일 실패 / 95일 실패.** `(end_de - bgn_de)`를 89일 이하로 유지한다 → `dart.MAX_LIST_SPAN_DAYS`
- 오류 코드 **100**은 "필드 부적정"이 아니라 이 기간 초과에도 쓰인다. 날짜 범위를 늘렸는데 100이 뜨면 이 제한을 먼저 의심할 것
- `corp_code`를 주고 조회하면 이 제한이 없다. 다만 기업별 조회로 돌아가면 호출 수가 기업 수에 비례해 12.2 전략이 무너지므로, 백필을 위해 기업별 조회로 전환하지 말 것
- 5~10분 주기 정상 폴링은 며칠 범위만 훑으므로 한도에 닿지 않는다. **문제가 되는 건 백필과 3개월 넘는 장애 공백 복구뿐이다**
- 긴 구간은 `dart.split_date_range(bgn, end)`로 89일 이하 창으로 분할해 순회한다. 창의 경계일은 하루 겹친다 — 중복 조회는 `rcept_no` unique로 무해하지만 누락은 영구적이므로 겹치는 쪽이 안전하다
- 백필 전용 명령을 새로 만들지 말고 `poll_dart --bgn/--end`를 쓴다 (멱등 `get_or_create` 경로를 한 곳으로 유지)
- 분할하면 호출 수가 `창 수 × 공시유형 10종 × 페이지`로 늘어난다. 긴 백필은 일일 한도를 감안해 나눠 실행한다

## 멱등성 패턴

수집 코드는 반드시 다음 패턴을 따른다:

```python
d, created = Disclosure.objects.get_or_create(rcept_no=..., defaults={...})
if created:
    # 신규일 때만 후속 처리 (원문 확보, 요약 enqueue)
```

이유: 폴링 중복·재시도에도 중복 저장이 없고, 중복 LLM 호출(비용)을 원천 차단한다.

## 검증 절차

DART 연동 코드를 작성/수정한 후:
1. `manage.py check` 통과 확인
2. 키가 있으면 실호출 1건으로 검증 (`poll_dart --days 1` 등), 없으면 산출물에 "실호출 미검증" 명시
3. 새 응답 필드를 쓰게 되면 실제 응답 샘플을 `_workspace/`에 기록 (다음 작업자의 명세가 된다)
