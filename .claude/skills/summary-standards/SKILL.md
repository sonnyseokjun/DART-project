# Summary Standards — 공시 요약 표준

공시 요약을 생성·검증하는 모든 작업의 기준. PLAN.md 5장(파이프라인 설계)과 11장(비용)의 실행 규칙이다.

## 산출물 구조 (DisclosureSummary와 1:1)

**LLM이 생성하는 필드**

| 필드 | 내용 | 제약 |
|------|------|------|
| one_line | 한 줄 요약 | 1문장, 200자 이내, 수치 포함 시 원문 근거 필수 |
| easy_explanation | 쉬운 설명 | 3~5문장, 전문 용어는 풀어서 |
| why_important | 왜 중요한가 | 일반 투자자 관점, 단정 금지 |
| importance | 중요도 | high/medium/low. **검수 대상 선정에는 쓰지 않는다** — 아래 "검수 게이트" 참조 |
| evidence | 원문 근거 배열 | `{field, claim, quote, quote_found, numbers_ok, missing_numbers}`. 저장해야 LLM 재호출 없이 재검증 가능 |

**코드가 채우는 필드 (LLM이 건드리지 않는다)**

| 필드 | 내용 |
|------|------|
| model_name / `PROMPT_VERSION` | 사용 LLM·프롬프트 판. 재현성 위해 항상 기록. 프롬프트 수정 시 버전을 올린다 (현재 `v2`) |
| review_warnings | 자동 검증 경고. `accuracy_warnings`(사실 경고)와 문체 경고를 구분해 다룬다 |
| is_reviewed / reviewed_by / reviewed_at | 사람 검수 결과와 책임 소재 |
| is_published / hidden_reason | 노출 스위치와 사유. **요약을 지우지 않고 감춘다** — 삭제하면 재수집 시 LLM을 다시 부른다 |
| edited_by_human / llm_original | 사람 수정 여부와 LLM 원본 스냅샷. 원본을 덮어쓰면 프롬프트 개선 근거가 사라진다 |

## 숫자 표기 규칙 (최우선)

**한국어 수 단위는 4자리로 끊고, 콤마는 3자리로 끊는다.** 이 둘이 어긋나는 지점이 이 프로젝트에서 실제로 발생한 오류의 유일한 원인이다.

```
45,453,450,000,000        ← 콤마는 3자리 (45 / 453 / 450 / 000 / 000)
4545|3450|0000|00  ✗      ← 콤마 기준으로 읽으면 "4조 5,453억" = 정확히 10배 틀림
45|4534|5000|0000  ✓      ← 4자리로 끊어야 "45조 4,534억"
```

실제 사고 3건(요약 id 128·81·107) 모두 **숫자 자체는 한 자리도 틀리지 않았고 자릿수 끊기에서만 무너졌다.** 결론은 하나다:

- **LLM에게 단위 환산을 시키지 않는다.** 원문 숫자를 그대로 인용하게 하고, 환산은 코드(`units.py`)가 한다. 코드가 하면 영원히 안 틀린다
- 증감률 등 **파생 수치도 LLM에게 계산시키지 않는다** — 같은 이유다
- 원문 표 머리의 **단위 선언(`(단위 : 억원)`, `(단위: 천원)` 등)을 검증기가 반영해야 한다.** 반영하지 않으면 맞은 요약에 경고가 붙는다(오탐)

## 프롬프트 필수 원칙

시스템 프롬프트에 반드시 포함한다 (PLAN.md 5.2):
1. 회계 비전공 일반인 대상 — "유상증자" 같은 용어는 첫 등장 시 풀어 쓴다
2. 과장·투자 권유 금지 — "호재", "매수 기회" 류 표현 금지. 사실과 의미만 전달
3. 불확실한 내용 단정 금지 — 원문에 없는 전망은 쓰지 않는다
4. 원문 인용 근거 — 모든 수치·핵심 주장에 원문 발췌 근거를 함께 출력하게 한다 (할루시네이션 억제)
5. 출력은 JSON 스키마 강제 — 파싱 실패는 재시도(최대 2회) 후 실패 기록
6. **산술 금지** — 단위 환산도 파생 수치 계산도 시키지 않는다. 원문 숫자를 그대로 인용하게 한다 (위 "숫자 표기 규칙")

## 비용 규칙

- **에이전트는 LLM을 실제로 호출하지 않는다.** `summarize_disclosures`는 하네스 훅으로 차단돼 있다. 사용자 비용이 발생하는 유일한 경로이고 실행 시점은 사용자가 정한다. 실호출이 필요하면 리더에게 사유·대상 건수·예상 비용을 보고만 한다
- **한 공시당 LLM 호출은 딱 한 번** — 요약 존재 여부를 먼저 확인하고, 있으면 재호출하지 않는다
- 검증 실패 시 재생성을 설계한다면 **재시도 상한을 반드시 둔다** — 무한 재시도는 곧 무한 비용이다
- 원문 전처리로 입력 토큰 절감: HTML/XML 태그 제거, 표는 텍스트화, 반복 상용구 삭제
- 중요도 low는 짧은 요약으로 충분 — 차등 처리로 토큰을 아낀다
- 분류·중요도 판정은 소형 모델, 최종 해설만 고성능 모델로 분리 가능 (티어링)

## 품질 검증 기준 (QA)

요약이 다음을 통과해야 게시 가능:
1. **숫자 대조**: 요약의 금액·비율·날짜가 원문 추출값과 일치 — 불일치는 심각도 '높음' 결함
2. **할루시네이션**: 원문에 근거 없는 사실·전망 없음
3. **금지 표현**: 투자 권유·과장 표현 없음
4. **링크·면책**: 원문 링크 병기, 면책 문구 노출 (UI 검증 항목)
5. **양방향 검증**: 오탐을 없애는 수정은 진짜 오류를 계속 잡는지 함께 확인한다. 한쪽만 보면 오탐을 미탐으로 바꿀 뿐이다

## 검수 게이트

검수의 목적은 **사람이 볼 건을 한 자릿수로 줄이는 것**이다. 전수 검수는 AI를 쓰는 의미를 지운다.

- **검수 대상 선정을 AI의 `importance`로 하지 않는다.** AI를 믿지 못해 검수하면서 대상 선정을 AI에 맡기는 것은 모순이다. **공시 유형**(유상증자·합병·감사의견 등 근거를 댈 수 있는 목록) 기준으로 정한다
- 검증 결과가 **게시를 실제로 막아야 한다.** 경고가 붙은 요약이 웹에 그대로 노출되면 검증은 장식이다 — 수치 불일치는 `is_published=False` + `hidden_reason`
- 경고의 성격을 구분한다: **수치 불일치는 사실 오류**(미게시), **인용 형식 경고는 사실 오류가 아니다**(게시하되 표시만)
- 검수 부담은 건수로 측정한다 — "경고가 몇 건에서 몇 건으로 줄었는지"를 `revalidate_summaries`로 보고한다

## 프롬프트 변경 절차

**실호출 없이 검증한다** (위 비용 규칙). 저장된 `evidence`·`raw_content`와 단위 테스트가 주된 근거다.

1. 프롬프트 문자열·출력 스키마의 단위 테스트, 요약 생성 경로는 모킹으로 검증
2. 저장된 요약 140건에 대해 `revalidate_summaries`로 검증기 쪽 효과를 **비용 없이 실측**한다
3. `PROMPT_VERSION`을 올린다 — 기존 요약과 구분 가능해야 한다
4. 결과를 `_workspace/`에 표로 기록. **실호출로 확인하지 않은 효과는 "예상"으로 표기**한다
5. 실호출 승인이 필요하면 리더에게 보고, 승인 후 사용자가 실행한다. 퇴행 발견 시 롤백
