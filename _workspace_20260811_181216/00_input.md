## 작업 범위

### 1. 요약 대상 선별 정책 (backend)

규칙 기반, LLM 호출 없음. 비용의 대부분이 여기서 결정된다.

- 공시유형 1차 필터: 지분공시·기타공시 기본 제외, 나머지 8종 대상
- 제목 블랙리스트: `임원ㆍ주요주주특정증권등소유상황보고서` 제외
- 화이트리스트 예외: 지분공시의 `주식등의대량보유상황보고서`
- **수정 (a)**: 블랙리스트를 부분 일치 → **정확 일치**로 좁힌다. 현재 한미반도체
  `임원ㆍ주요주주특정증권등거래계획보고서`(`20260702000197`)가 부분 일치로 우연히 걸린다.
  전자는 사후 신고, 후자는 사전 매도 계획 보고로 성격이 다르다.
  `[기재정정]` 접두사를 제거한 뒤 비교할 것
- **수정 (b)**: 기타공시 `자기주식처분결과보고서`를 화이트리스트 예외로 편입
  (`20260710000585`, `20260716000796`). 주요사항보고서(자기주식처분결정)를 대상에
  넣었으므로 결과 보고도 넣는 것이 일관된다. 유형 제외 규칙에 제목 예외를 둘 수 있는 구조 필요
- **판단 (c)**: 공정위공시 17건(계열사 내부거래)은 analyst가 원문 확인 후 포함/제외 판단
- `Disclosure`에 대상 여부·제외 사유 필드 추가 + 마이그레이션.
  기록하지 않으면 "미요약"과 "의도적 제외"를 구분할 수 없고 매 실행마다 전건 재평가한다
- 정책은 단일 출처(상수/전용 모듈)로 두고 테스트로 고정

### 2. 원문 확보·전처리 (backend, analyst 명세 기반)

- 요약과 **별도 관리 명령**으로 분리한다 (재시도 용이)
- `dart.fetch_document` 연결, `raw_content` 저장·`raw_fetched` 설정
- **인코딩 실측 확인 필수**: 현재 `decode('utf-8', errors='replace')` 하드코딩.
  DART 원문이 EUC-KR/CP949일 가능성이 있어 한글이 깨질 수 있다
- XML 정제·표 텍스트화·상용구 제거로 입력 토큰 절감

### 3. LLM 요약 (ai-prompt + backend)

- **OpenAI API를 사용한다** (PLAN.md 3장 스택 표대로). 사용자 확정 사항이며 재검토하지 않는다
- `requirements.txt`에 `openai` 추가, `OPENAI_API_KEY`를 `.env`→`settings`로 노출
  (`DART_API_KEY`와 동일 패턴), `.env.example` 갱신
- **모델 ID·가격·파라미터는 기억에 의존하지 말고 OpenAI 공식 문서에서 확인하라.**
  모델 라인업과 단가는 자주 바뀐다. 선택 기준:
  (a) 한국어 요약 품질, (b) JSON 스키마 강제(Structured Outputs) 지원 여부,
  (c) 토큰 단가, (d) 사업보고서 원문이 들어갈 컨텍스트 크기.
  선택한 모델과 근거·확인한 문서 출처를 산출물에 기록하라
- **출력은 JSON 스키마로 강제한다.** 프롬프트로 "JSON으로 답해줘"라고 부탁하는 방식은 쓰지 않는다.
  파싱 실패는 최대 2회 재시도 후 실패로 기록
- `model_name` 필드에 실제 사용한 모델 ID를 기록한다 (재현성)
- 길이 제약을 프롬프트와 스키마에 이중으로 건다: `one_line` 200자 이내,
  `easy_explanation` 3~5문장
- 요약 지침(시스템 프롬프트)은 전 공시 공통이다. 프롬프트 캐싱이 지원되면 활용하되,
  지침에 날짜·기업명 등 가변 값을 넣지 말고 원문·메타데이터는 user 메시지에 둔다.
  캐싱 지원 여부와 적중 실측 결과를 산출물에 기록
- 응답에 안전 거부·필터링이 걸릴 수 있다. 응답 본문을 읽기 전에 정상 완료 여부를 먼저 확인하고,
  거부·중단 시 예외로 죽지 않고 건별로 기록한다
- 토큰 계산은 **`tiktoken`** 을 사용한다 (OpenAI 정식 토크나이저)
- 산출물 구조·프롬프트 5원칙·품질 기준은 `summary-standards` 스킬을 따른다
- PLAN.md 3장은 이미 OpenAI API로 적혀 있어 수정할 필요가 없다

### 4. 백필 기능 (backend, 병렬 작업)

`list.json`은 `corp_code` 없이 조회 시 **검색기간 3개월 제한**(오류 코드 100).
실측 경계: **89일 통과 / 92일 실패**.

- PLAN.md 12.2 날짜별 일괄 폴링 전략 자체는 유효 (정상 폴링은 한도에 닿지 않음)
- 문제는 백필·장애 복구. PLAN.md 4.4의 "놓친 구간을 날짜 범위로 다시 훑는다"는
  공백이 3개월을 넘으면 동작하지 않는다
- `poll_dart`에 `--bgn`/`--end`(YYYYMMDD) 추가, `--days`와 상호 배타
- 3개월 초과 범위는 89일 이하 창으로 **자동 분할 순회**. `--days 150`도 오류 없이 동작
- 별도 명령을 새로 만들지 말고 기존 `poll_dart` 한 경로에서 처리 (멱등 로직 중복 방지)
- **청크 경계 누락 금지.** `rcept_no` unique로 중복은 무해하므로 경계일을 겹쳐 누락을 차단.
  경계 동작을 테스트로 고정
- PLAN.md 4.4·12.2와 `dart-api-know-how` 스킬 "호출량 규칙"에 제약·실측 경계·오류 코드 문서화

### 5. 비용 리스크 (전원)

요약 대상 136건 중 정기공시 11건(분기보고서 10 + 사업보고서 1)의 원문이 수십~수백 페이지다.
통짜로 LLM에 넣으면 나머지 125건 합계를 훨씬 넘길 수 있다.

- `tiktoken`으로 유형별 토큰 규모를 먼저 실측한다 (정제 전/후 모두)
- 정기공시는 전처리로 핵심 섹션만 추출하는 별도 처리가 필요할 수 있다 — 실측 후 판단
- **LLM 실호출 전 예상 비용(대상 건수 × 추정 토큰 × 단가)을 사용자에게 보고하고 승인받는다**

   재실행 시 기존 요약이 있는 공시는 LLM을 재호출하지 않는다 (멱등)
4. 서로 다른 유형 최소 3건에 대해 품질 검증: 숫자 대조(금액·비율·날짜 = 원문 추출값),

   청크 경계 누락·중복 없음이 테스트로 고정된다
8. `disclosures/tests.py`에 회귀 테스트 추가. **LLM·DART 실호출 없이 목(mock)으로** 고정하고

## 제약

- **사용자 요청 경로에서 DART·LLM을 직접 호출하지 않는다.** 수집·원문 확보·요약은 관리 명령
  (추후 Celery)에서만. 뷰는 로컬 DB만 읽는다 (PLAN.md 12.1 핵심 설계 원칙)
- **한 공시당 LLM 호출 1회.** 요약 존재 여부를 먼저 확인하고 재호출하지 않는다
  (`DisclosureSummary` OneToOne이 근간)
- 원문 확보·요약 파싱 실패는 예외로 죽지 않고 건별 기록 후 다음 건 계속 처리
- 모델 필드·admin에 한국어 `verbose_name`. 주석·docstring·커밋 메시지도 한국어
- 실호출 중 문제(인코딩, 스키마 불일치, 예상 밖 비용) 발생 시 사용자에게 즉시 보고·질문
- SQLite 단일 파일이므로 마이그레이션과 대량 수집을 동시에 돌리지 않는다 (락 경합)
