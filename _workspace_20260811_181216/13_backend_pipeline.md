## 2. 선별 정책 (`disclosures/selection.py`)

### 판정 로직

순수 함수 `evaluate(disclosure_type, report_name) -> (SelectionState, ExclusionReason|'')`. 모델·DB에 의존하지 않아 테스트로 그대로 고정된다.

**판정 순서**

1. **제목 블랙리스트** — 정규화 제목이 `TITLE_BLACKLIST`와 **정확히 일치**하면 제외 (`blacklist`)
2. **공시유형 제외** — `EXCLUDED_TYPES`(지분공시·기타공시)이고 `TYPE_WHITELIST_PREFIXES`에 걸리지 않으면 제외 (`excluded_type`)
3. 나머지는 모두 대상

블랙리스트를 유형 제외보다 **먼저** 본다. 둘 다 해당하는 지분공시 정형 공시를 "정형 반복 공시"로 기록해야 제외 사유 분포가 읽히기 때문이다(유형 제외를 먼저 보면 821건이 전부 `excluded_type`으로 뭉개진다).

### 제목 정규화 (`normalize_title`)

1. **모든 공백 제거** — DART 제목에는 `소송등의판결ㆍ결정      (주주총회결의취소)`처럼 정렬용 연속 공백이 섞여 있다
2. **선행 대괄호 태그 제거** — `^(?:\[[^\]]*\])+` 로 `[기재정정]`·`[발행조건확정]`·`[기재정정][첨부정정]`을 모두 벗긴다

### 매칭 방식 (docstring에 명시)

| 규칙 | 방식 | 이유 |
|---|---|---|
| 블랙리스트 | **정확 일치** | 부분 일치를 쓰면 `임원ㆍ주요주주특정증권등거래계획보고서`(사전 매도계획)가 `…소유상황보고서`(사후 신고)에 우연히 걸린다 |
| 화이트리스트 | **정규화 후 접두어 매칭** | `주식등의대량보유상황보고서(약식)`처럼 접미가, `[기재정정]자기주식처분결과보고서`처럼 접두가 붙어 정확 일치로는 못 잡는다 |

### 정책 상수

```
EXCLUDED_TYPES         = {지분공시, 기타공시}
TITLE_BLACKLIST        = {임원ㆍ주요주주특정증권등소유상황보고서}
TYPE_WHITELIST_PREFIXES = {
    지분공시: (주식등의대량보유상황보고서, 임원ㆍ주요주주특정증권등거래계획보고서),
    기타공시: (자기주식처분결과보고서,),
}
```

#### 이름이 비슷한 두 서류를 반대로 취급한다

`임원ㆍ주요주주특정증권등소유상황보고서`(제외)와 `임원ㆍ주요주주특정증권등거래계획보고서`(대상)는 이름이 거의 같지만 **정보의 방향이 반대**다.

| | 소유상황보고서 | 거래계획보고서 |
|---|---|---|
| 시점 | 이미 일어난 보유 변동의 **사후** 신고 | 대량 매도를 하겠다는 **사전** 보고 |
| 표본 건수 | 821 (전체의 85%) | 2 |
| 판정 | 블랙리스트 제외 | 화이트리스트 대상 |

앞으로 일어날 일을 미리 알리는 쪽이 일반 투자자 관점의 신호 가치가 높고, 2건뿐이라 비용 영향도 없다. 이름이 비슷해 나중에 "중복 아닌가" 하고 정리될 위험이 있으므로 판정 근거를 `selection.py`의 화이트리스트 주석에 남기고, 두 서류가 갈리는 것을 `test_lookalike_reports_are_split_opposite_ways`로 고정했다.

공정위공시 17건은 지시대로 **이번 단계 대상에 포함**했다(제외는 원문 확인 후 후속 판단). 실측 결과 건당 441토큰으로 비용 부담은 없다.

### 모델 필드

- `selection_state` (`pending` 미판정 / `target` 요약 대상 / `excluded` 제외) — Boolean 대신 3상태를 쓴 이유는 "아직 안 본 공시"와 "의도적 제외"를 구분해야 재실행 시 재평가를 건너뛸 수 있기 때문이다
- `exclusion_reason` (`blacklist` / `excluded_type` / 대상이면 `''`)
- 인덱스 `(selection_state, raw_fetched)` — `fetch_documents`의 대상 조회용

## 3. 원문 확보·전처리 (`fetch_documents`)

### 명령 사양

```
python manage.py fetch_documents --limit 5              # 건수 제한 (검증용)
python manage.py fetch_documents --type 거래소공시       # 유형 필터
python manage.py fetch_documents --rcept-no 2026...     # 1건 지정
python manage.py fetch_documents --refetch              # 전처리 로직 변경 시 재확보
```

- 대상 조회: `selection_state=target` **AND** `raw_fetched=False`. 이미 확보한 원문은 재호출하지 않는다(`--refetch` 명시 시에만)
- 건별 실패는 `except Exception`으로 잡아 stderr에 기록하고 다음 건을 계속 처리한다. 실패 건은 `raw_fetched=False`로 남아 다음 실행에서 자동 재시도된다
- 호출 간 0.2초 간격
- 요약 명령은 만들지 않았다(리더가 배선)

### 인코딩 (실측 확인)

**UTF-8이 맞다.** `fetch_document`의 `decode('utf-8')`을 유지했다. 다만 거래소공시류 HTML 원문은 헤더에 `charset=euc-kr`로 **잘못 선언**하면서 실제 바이트는 UTF-8이다. 선언을 믿고 디코딩하면 한글이 전부 깨진다. 이 사실을 `dart.fetch_document` docstring과 `dart-api-know-how` 스킬 "응답 형태의 함정" 절에 남겼다.

### 전처리 (`dart.strip_markup`)

1. `<script>`/`<style>`/`<!-- -->` **내용째로 제거**
2. **모든 공백(줄바꿈 포함)을 공백 1개로 압축** — 원문의 줄바꿈은 마크업 들여쓰기일 뿐이다. 이 단계를 빼면 `<TD>값</TD>\n<TE>값</TE>` 사이의 줄바꿈이 표의 한 행을 여러 줄로 쪼갠다(초기 구현에서 실제로 발생)
3. 표 셀 종료 `</td|th|tu|te>` → ` | ` — **DART XML은 `TD`/`TH` 외에 `TU`(단위값)·`TE`(추출값) 셀을 쓴다.** 구분자를 넣지 않으면 `1,234`와 `5,678`이 `1,2345,678`로 붙어 숫자 대조가 불가능해진다
4. 블록 요소 종료(`</tr|p|div|table|title|section-*|li|h*>`, `<br>`, `<pgbrk>`) → 줄바꿈
5. 잔여 태그 제거 → HTML 엔티티 언이스케이프
6. 줄 단위 정리: 연속 공백 압축, 양 끝 구분자·공백 제거, 빈 줄·빈 셀만 남은 행(`| | |`) 삭제

결과 예 (표의 수치가 행 단위로 보존됨):

```
구 분 | 제58기 | 제57기 | 제56기
[유동자산] | 306,220,075 | 247,684,612 | 227,062,266
ㆍ현금및현금성자산 | 73,306,751 | 57,856,378 | 53,705,579
```

HTML·DART XML 두 포맷 모두 같은 함수가 처리한다(`dart.is_dart_xml()`로 포맷 판정).

#### `3. 원재료 및 생산설비` 포함은 확정 사항이다 (빼지 말 것)

이 섹션 하나가 정기공시 건당 **7,530 → 11,424토큰**을 만든다. 비용만 보면 뺄 후보로 보여 ai-prompt가 제외를 제안했으나, 리더가 포함을 확정했다.

| 구성 | 토큰(삼성 분기보고서) | 정기공시 11건 입력 비용 |
|---|---|---|
| 원재료 포함 (현재) | 11,424 | $0.126 |
| 원재료 제외 | 7,530 | $0.083 |

차이 $0.043은 141건 총액 $1.35의 3%로 판단 근거가 되지 못한다. 반도체는 설비 투자와 원가 구조가 실적 변동의 핵심 동인이고 추적 대상 10곳이 전부 반도체다. 생산능력·가동률·주요 원재료 가격 추이가 없으면 요약의 "왜 중요한가"를 원문 근거로 쓸 수 없어, **모델이 근거 없이 추측할 위험이 오히려 커진다.** 같은 근거를 `dart.PERIODIC_KEY_SECTIONS` 주석에도 남겼다.

**감소율** (분기보고서 표본 `20260515002181`)

|---|---|---|
| 원문 | 4,318,370 | — |

실제 저장한 다른 분기보고서(`20260514000391`)는 1,365,697자 → 13,104자 / **7,757토큰**이다. 두 건 모두 ai-prompt가 제시한 2만~3만 토큰 목표 아래다.

### 4.2 발행공시 (증권신고서) — **지시 범위 밖에서 발견한 문제**

지시서는 정기공시만 대형 서식으로 지목했으나, 실호출 결과 **증권신고서가 더 컸다**: `20260624000511`(SK하이닉스 유상증자) 4,157,032자 → 전체 정제 시 **413,650토큰**. 분기보고서(246,375)의 1.7배다. 대상 6건 전부를 통짜로 넣으면 나머지 133건 합계의 6배가 넘는다. 그대로 두면 파이프라인이 이 유형에서 작동하지 않으므로 같은 섹션 추출 경로를 확장했다.

구조 실측 — 증권신고서는 **제1부(모집·매출에 관한 사항) + 제2부(발행인에 관한 사항)** 이고, **제2부가 사업보고서 전체를 그대로 반복**한다(제2부 `III. 재무에 관한 사항`만 1,607,147자). 로마 숫자가 두 부에서 중복되므로(`I. 모집 또는 매출에 관한 일반사항` vs `I. 회사의 개요`) 제목 전체로 접두어를 비교해야 구분된다.

**선정한 섹션** (`dart.OFFERING_KEY_SECTIONS`) — 전부 제1부:

| 섹션 | 토큰 | 근거 |
|---|---|---|
| `1. 핵심투자위험` | 13,207 | 금감원이 요구하는 평이체 위험 요약. 일반인 요약에 그대로 쓰인다 |
| `I. 모집 또는 매출에 관한 일반사항` | 12,556 | 공모 규모·방법·가격 결정 |
| `V. 자금의 사용목적` | 20,510 | 조달 자금의 용처 |

독자가 알아야 할 "얼마를, 어떤 조건으로, 무엇에 쓰려고 발행하나 / 무엇이 위험한가"는 전부 제1부에 있다. 제2부는 같은 기업의 정기공시로 별도 요약되므로 버렸다.

**감소율**

| | 자수 | 토큰 |

| 원문 | 4,157,032 | — |
| 전체 정제 | 702,126 | 413,650 |
| 섹션 추출 | 79,725 | **46,273** |

이미 전체 정제로 저장했던 2건(`20260624000511`, `20260630001095`)은 `--refetch`로 다시 받아 섹션 추출본으로 교체했다.

**안전장치**: 매칭되는 섹션이 하나도 없으면 `extract_key_sections`가 `None`을 반환하고 호출자는 원문 전체 정제로 되돌아간다. 발행공시 6건 중 `투자설명서`·`증권발행실적보고서`는 서식이 달라 이 경로를 탈 수 있다(미확보 상태라 미검증).

## 4.5 요약 모듈 연동 (`DisclosureSummary` 필드 추가)

`summarizer.summarize_disclosure()`의 반환값 중 저장할 곳이 없던 두 가지를 받도록 필드를 추가했다 (마이그레이션 `0003`).

| 필드 | 타입 | 담는 것 |
|---|---|---|
| `evidence` | `JSONField(default=list)` | 원문 인용 근거 배열 `[{field, claim, quote, quote_found, numbers_ok, missing_numbers}]` |
| `review_warnings` | `JSONField(default=list)` | 자동 검증 경고 (`unsupported_numbers`, 인용 미발견, 문장 수 일탈) |

버리면 두 가지가 깨진다. QA가 숫자 대조를 재검증할 때마다 LLM을 다시 호출해야 해서 **공시당 1회 원칙이 무너지고**, 사후에 요약 오류가 나와도 어느 원문 구절에서 나온 값인지 추적할 수 없다.

**`DisclosureSummary.needs_review` 프로퍼티** — `is_reviewed` 불리언만으로는 "아직 검수 안 함"과 "검수가 필요함"이 구분되지 않는다. 중요도 `high`(PLAN.md 11 검수 게이트) **또는** 검증 경고가 붙었고 아직 미검수인 요약을 `True`로 판정한다.

**admin 노출** (`DisclosureSummaryAdmin`)
- `list_display`에 `warning_count`(`⚠ n` / `-`)와 `needs_review`(불리언 아이콘) 계산 필드 추가
- `HasWarningsFilter` — JSONField는 기본 `list_filter`로 걸 수 없어 전용 `SimpleListFilter`를 뒀다. 검수 담당자가 가장 먼저 찾아야 하는 것이 "경고가 달린 요약"이다
- `evidence`·`review_warnings`는 `readonly_fields` — 자동 생성물이라 손으로 고칠 대상이 아니다

## 7. 남은 일 / 후속 판단 거리

1. **정기공시 표 인용 충실도 — 요약 실행 전 관문.** ai-prompt의 스모크 테스트 3건이 전부 짧은 공시였던 탓에, 표가 많은 정기공시 원문에서 모델이 인용을 충실히 뽑는지는 미검증이다. 리더가 `summarize_disclosures`로 **정기공시 1건을 먼저 돌려 `quote_found` 비율과 `unsupported_numbers`를 확인한 뒤** 나머지를 진행하기로 했다. 무너지면 프롬프트 §4(인용 규칙) 보강이 필요하다
2. **나머지 원문 미확보 126건** — `fetch_documents`를 옵션 없이 돌리면 전량 확보된다. 정기공시 10건·발행공시 4건이 각 4~7MB 다운로드라 실행 시간이 걸린다. 요약 실호출 직전에 리더가 판단
3. **발행공시 `투자설명서`·`증권발행실적보고서`** — 서식이 달라 섹션 맵이 안 걸릴 수 있다(그 경우 전체 정제로 폴백). 확보 후 토큰 수를 확인해야 한다
4. **기타공시 `주식매수선택권부여에관한신고` 1건** — 현재 유형 제외. 재검토하려면 `fetch_documents --refetch --rcept-no 20260514001281`로 원문 1건만 받아 보면 된다 (§2 참조)
5. **공정위공시 17건 포함 여부** — 지시대로 대상에 넣었다. 건당 441토큰으로 비용 부담은 없으니 요약 품질을 보고 판단하면 된다
6. **지분공시 대량보유보고서 27건(223K 토큰)** — 추가 절감이 필요할 경우의 다음 후보
