### 3.5 ⚠ 구현 함정 — 내가 직접 밟았다

규칙 3.3을 구현하며 **두 번 잘못된 결과를 냈다.** backend는 같은 실수를 피해야 한다.

**함정 1 — 인용문을 첫 조각으로 위치 추정하면 안 된다.**
처음에 인용문의 **첫 조각**으로 위치를 잡았더니 id 34(DB하이텍)의 인용문
`합 계 | 4,177 | 1,135 | - | -`이 `합계`라는 흔한 라벨의 **문서 앞쪽 출현**에 붙어
백만원 구간으로 판정됐다. 실제 이 행은 `(단위 : 억원)` @7128 아래이고 **AI가 맞았다.**
→ 각 수치는 **자기 자신이 들어 있는 조각의 위치**로 배수를 조회해야 한다.
이 수정만으로 오탐 판정이 50건 → 17건으로 줄었다.

**함정 2 — 짧은 숫자 조각은 부분 문자열로 매칭된다.**
`_content_only`가 서식을 지우면 원문이 한 줄로 이어져, `120` 같은 조각이
`...41207...` 같은 긴 숫자 안쪽에 걸린다. id 8의 `120억` 검증이 이렇게 엉뚱한 위치를 잡았다.
→ **토큰 경계를 확인**하고 찾아야 한다(앞뒤가 숫자·쉼표가 아닌 위치).

**함정 3 — 인용문이 선언 자체를 포함하기도 한다.**
id 52의 인용문은 `'(단위 : 백만 원)\n라. 거래금액 | 390,242'` 로 선언을 **품고 있다.**
`직전 선언` 조회에서 경계 조건(`offset <= 위치`)을 잘못 잡으면 이 건을 놓친다.

### 3.6 헤더 파싱의 진짜 가치 — 탐지력

0.3절대로 헤더 파싱은 **오탐을 0건 줄인다.** 그런데도 해야 하는 이유는 이것이다.

현재 `_value_supported`는 `_SCALE_MULTIPLIERS`의 **다섯 배수를 무조건 허용**한다.
백만원 표의 값 `q`에 대해 정답은 `q×10⁶` 하나뿐인데, 검증기는
`q×10³`·`q×10⁴`·`q×10⁶`·`q×10⁸`·`q×10¹²`를 **전부 정답으로 인정한다.**
즉 **1,000배 틀려도 통과한다.** 실제 오류 6토큰이 걸린 건 순전히 **10배가 목록에 없어서**다.

헤더를 읽으면 후보 배수가 **메뉴가 아니라 정확히 하나**로 좁혀진다.
그러면 `_SCALE_MULTIPLIERS`를 **넓히는 게 아니라 좁히거나 폐기**할 수 있다.

### 3.7 ⚠ 절대 하면 안 되는 대안 — 배수 목록 넓히기

| 사례 | 요약값 ÷ 원문값 | 목록에 넣으면 |
|---|---|---|
| 37 영업이익·순이익 (**진짜 오류**) | ≈ 10⁵ | `10**5` 추가 시 **오류 통과** |
| 81·107·128·**117** (**진짜 오류**) | ≈ 10⁻¹ | `10**1` 추가 시 **오류 통과** |
| 37 투자액 (정답) | 10⁹ | `10**9`는 **안전** |
| 38 (정답) | 10⁶ × 0.951 | 10⁶ + **근사 허용오차** 필요 |

**`10**5`와 `10**1`은 넣는 순간 진짜 오류 7토큰이 전부 사라진다.**

## 4. 미탐 조사 — 조용히 통과한 오류가 있는가 (리더 질문 2)

### 4.1 노출 규모

경고 없이 통과한 수치 중 **164개가 `_SCALE_MULTIPLIERS` 배수 경로에만 의존**해 통과했다
(그중 153개는 경고가 전혀 없는 요약 32건에 속한다). 이 164개는 **배수가 맞는지 아무도 확인하지 않은** 수치다.

### 4.2 확인된 미탐 1건 — id 117

`4. 자금조달의 목적 | 시설자금 (원) | 40,023,070,290,000` = **40조 230억 7,029만**인데
요약은 `40,023,070,290,000원(약 4조 원)`이라고 썼다. **10배 축소. 경고 없음.**

**통과한 메커니즘을 코드로 확인했다:**

```
인용문에서 뽑힌 값: [1, 2.72, 3, 4, 5, 6, 7, 9, 11, 12, 14, 15, 29, 2026,
                    2190229, 2249751, 17790000, 40023070290000]
약 4조(=4e12) 통과 여부: True
통과 근거: 인용토큰 '4'(값 4) x 1,000,000,000,000 -> 4e+12 == 요약값 4e+12
```

**표 행의 항목번호 `4.`(`4. 자금조달의 목적`)가 값 `4`로 추출되어, `4 × 조원 = 4조`라는
가짜 근거를 만들어 냈다.** 검증기가 오류를 못 잡은 게 아니라 **오류를 정당화해 줬다.**

`is_reference_number`가 `0~31`의 맨 정수를 대조 **대상**에서는 빼지만,
**근거(quote_values)에서는 빼지 않는다.** 이 비대칭이 원인이다.

### 4.3 같은 실패 모드 전수 스캔

"잡음 정수에만 기대어 통과한 수치"를 전수 검색해 4건을 찾았고, 손으로 확인했다.

| id | 수치 | 근거로 쓰인 값 | 판정 |
|---|---|---|---|
| **117** | `4조` | **`4`(항목번호)** | **진짜 오류 (미탐)** |
| 10 | `57.23조` | `57.23` | 정상 — `단위 : 조원` 표의 실제 값 |
| 113 | `89.40조` | `89.40` | 정상 — 〃 |
| 110 | `5,000` | `5` | 정상 — `43조 1,407억 5,000만`의 꼬리. 요약은 맞음 |

**확정 미탐은 1건이다.** 다만 이 스캔은 **한 가지 실패 모드만** 겨냥했다.
`_SCALE_MULTIPLIERS`가 열어 준 나머지 경로(정상 값에 잘못된 배수를 적용한 경우)는
전수 확정하지 못했다 — 3.5의 위치 추정 한계 때문이다. **1건은 하한이다.**

### 4.4 함의

이번 작업의 목표는 "오탐 줄이기"만이 아니다. **미탐을 잡는 것도 포함되어야 한다.**
그리고 미탐을 잡는 수단이 곧 헤더 파싱이므로, backend의 대기 작업은
가치가 없어진 게 아니라 **목적이 바뀐 것**이다.

### 5.0 ⚠ `prompt-noarith` 분류와의 불일치 — 6건

리더를 통해 전달된 `prompt-noarith`의 분류는 **80·109·111·115·123·125를 "AI 파생 계산"**으로 본다.
리더의 방법론 지적("원문에 문자열이 있는지로 판정하지 마라, 대형 문서에선 우연히 있다. 검산이 답이다")은
**원칙적으로 옳고 나도 동의한다.** 다만 내 판정 근거는 문자열 존재가 아니라 **라벨이 붙은 위치의
문맥**이었고, 그중 두 건은 검산으로도 "AI가 계산하지 않았음"이 확정된다.

**id 80 `2.44` — 검산이 오히려 '계산 아님'을 증명한다**

원문(@15244):
> 본건 신주의 최대 발행수량 17,790,000주는 작성기준일 현재 **발행주식총수 712,702,365주의 약 2.50%**에
> 해당하며, **기존 주주의 지분율은 약 2.44% 하락**하고

| 제수 | 계산 결과 | 출처 |
|---|---|---|
| 728,002,365 (제시된 값) | 2.4437% | **원문에 없는 숫자** |
| 712,702,365 (원문의 발행주식총수) | **2.4961%** | 원문이 이 값을 "약 2.50%"로 적음 |
| 730,492,365 (증자 후) | 2.4353% | 원문에 없음 |

**원문의 발행주식총수로 계산하면 2.50%가 나오지 2.44%가 나오지 않는다.**
AI가 계산했다면 2.50%를 썼어야 한다. 2.44%는 원문 문장을 **읽어서** 옮긴 것이다(같은 문장 @74301에도 재등장).

**id 125 `0.019` — 원문이 그 값을 직접 적고 있다**

> `- 상기 '1. 처분예정주식(주)'은 발행주식총수(보통주 5,846,278,608주)의 **0.019% 수준**이며`

제시된 제수 5,969,782,550은 원문에 없다. 원문의 5,846,278,608로 계산하면 0.01937%,
제시된 제수로는 0.01897% — 둘 다 0.019로 반올림되어 **검산으로는 구별되지 않는다.**
그러나 원문이 `0.019%`라는 문자열을 **라벨과 함께** 적고 있다.

**나머지 4건 — 라벨이 붙은 표 행에 그대로 있다** (문자열 우연 일치가 아니다)

| id | 값 | 원문의 위치 |

**그러나 대응이 갈린다:**
- "AI 파생 계산"으로 보면 → 프롬프트에 "계산하지 마라"를 넣는다. 그런데 **경고는 그대로 남는다.**
  계산을 안 해도 그 값이 인용되지 않으면 여전히 `인용 근거 없는 수치`가 뜬다.
- "인용 커버리지 누락"으로 보면 → **"수치를 쓰면 그 수치가 적힌 행을 인용하라"**를 넣는다.
  이건 6건 전부를 해소한다. 원문에 값이 있으므로 인용할 대상이 **존재한다.**

**후자를 권한다.** 판단이 뒤집히면 알려 달라 — 그 경우 `units.py`에 파생 계산기가
필요해지므로 backend 범위가 달라진다.

### 5.1 코드가 대신 계산할 것은 **없다**

증감률·희석률·환율은 전부 공시 원문이 제공한다(DART 서식이 증감 행·비율 열을 강제한다).

- **ai-prompt:** "증감률을 계산하지 마라"는 **불필요한 지시**다. 계산은 일어나지 않았다.
  실제로 필요한 것은 **"수치를 쓰면 그 수치가 적힌 행을 인용하라"**다(D 원인 15토큰).
- **backend:** `units.py`는 **원 단위 정수 → 한국어 표기** 환산만 하면 된다. 증감률 계산기는 근거 없다.

AI가 만든 표현이 하나 있다 — id 105/111/115의 `%포인트`. 원문은 `-1.16`·`2.82`만 주고
"%포인트"라는 말은 없다. **값은 원문 그대로**라 수치 검증에는 영향이 없다.

## 7. 판단이 갈렸던 지점

### 7.1 id 38 `7억` — 오탐으로 분류했으나 여지가 있다

`736`(백만원)=7.36억을 `약 7억`으로 썼다. 4.89% 과소.
- 오탐 근거: 바로 앞에 `736백만 원`을 정확히 병기했고 `약`이 붙었으며, 코드 자신의
  `APPROX_TOLERANCE`(5%) 안이다. 경고가 난 건 근사 오차가 **스케일 경로에 미적용**이라서다.
- 반론: 일반 독자에게 5% 오차를 준다.
- **판정: 오탐.** 다만 이 한 건만 보고 `SCALE_TOLERANCE`를 5%로 키우면 다른 곳에서 오류를 놓친다.
  **허용오차 값은 backend가 별도 판단할 것.**

### 7.2 D(인용 커버리지 누락, 15토큰/10요약) — 검증기 문제가 아닐 수 있다

검증기는 지금 **설계대로** 동작한다. 경고 문구부터 `인용 근거 없는 수치`다.

- **전역 폴백(raw_content 전체 대조):** 15토큰이 즉시 사라지지만 할루시네이션 검출력을 잃는다.
  실증: id 38의 `7억`은 전역 배수 대조에서 "원문 어딘가의 `7` × 억원"이라는 **엉뚱한 이유로**
  통과한다. 79,725자짜리 증권신고서(id 80)에서는 거의 모든 숫자가 우연히 맞는다.
  **4.2의 id 117이 정확히 이 함정의 실제 사례다.**
- **위치 제한 폴백:** 인용문 근처만 대조. id 78은 약 80자 거리라 통할 것이다.
  **다만 15토큰 전부에 대해 창 크기를 검증하지 않았다 — 추정이다.**
- **프롬프트:** "본문에 쓰는 모든 수치는 그 수치가 적힌 행을 인용하라." 근본 대응이나
  효과는 실호출 전까지 측정 불가.

**권고: D는 프롬프트 문제로 취급하고 전역 폴백은 넣지 마라.**
검증기만의 목표치는 **19 → 14**로 잡고, D는 프롬프트 개선 후 재측정 대상으로 남긴다.

### 7.3 id 37을 요약 단위로 '진짜 오류'로 집계한 근거

한 요약에 진짜 오류 2토큰과 오탐 1토큰이 공존한다. 사람 검수가 필요하므로
**하나라도 진짜 오류면 진짜 오류**로 처리했다. 토큰 집계(6/23)와 요약 집계(4/15)를 섞지 말 것.

### 7.4 확실한 것 / 추정인 것

**확실한 것 (코드에 값을 넣어 실행 확인)**
- 요약 단위 진짜 오류 4 / 오탐 15 / 판정 불가 0, 미탐 1(id 117)
- 토큰 단위 원인 A1·B6·C1·D15·E6
- **id 8의 원인이 헤더가 아니라 인용 커버리지 누락이라는 것** (인용문 값에 `4,000` 부재)
- **id 117이 항목번호 `4` × 조원으로 통과했다는 것**
- 진짜 오류 7토큰이 전부 10⁵ 또는 10⁻¹ 비율
- 2.2 정규식 전수 검증(오검출 0), 문서당 단위 2종 이상 30/141, id 37의 선언 11개 배치
- 배수 경로에만 의존해 통과 중인 수치 164개
- `10**5`·`10**1`을 넣으면 진짜 오류가 전부 통과한다는 것
- 인용 경고 14건의 4패턴

**추정 (검증 안 함)**
- 미탐이 1건뿐이라는 것 — **하한이다.** 한 가지 실패 모드만 스캔했다
- 위치 제한 폴백의 적정 창 크기 (7.2)
- `%` 제거 정규화의 부작용 (P3)
- 근사 오차를 스케일 경로에 적용할 때의 적정값 (7.1)
- **헤더 규칙이 경고 없는 121건에 새 경고를 만들지 않는다는 것.**
  3.3에서 17건 불일치가 나왔고 대부분 내 도구 결함이었지만 **전부 해소하지는 못했다.**
  backend는 `revalidate_summaries`로 **양방향** 확인해야 한다 —
  오탐 15건을 없애면서 새 오탐 N건을 만들면 아무것도 개선되지 않는다.

## 8. backend·ai-prompt에게 넘기는 요약

**backend**
1. **헤더 파싱은 경고를 1건도 줄이지 않는다** (0.3). 목적은 **탐지력**이다 (3.6) — id 117을 잡고
   `_SCALE_MULTIPLIERS`를 좁히기 위한 것이다.
2. `_SCALE_MULTIPLIERS`에 `10**5`·`10**1`을 **절대 넣지 마라** (3.7). `10**9`는 안전.
3. **경고를 실제로 줄이는 건 다른 두 가지다:**
   - `extract_numbers` 꼬리 절단 수정 → **4건** (`verification.py`에서 마지막 무단위 조각을
     합산하지 않는 지점. `nxt_unit is None` 에서 break)
   - 근사 허용오차를 스케일 경로에 적용 → **1건** (값은 backend 판단, 7.1)
4. 2.2의 `UNIT_DECL`·`MONEY_TOKEN`을 그대로 써도 된다 — 141건 전수 오검출 0.
5. 적용 규칙은 **"수치 자신의 조각 위치의 직전 선언"** (3.2). 문서 전역은 30/141에서 틀린다.
6. 비금액 선언(`시간`·`%`·`주`·`USD`)도 수집해 **배수 1로 리셋** (W1).
7. **구현 함정 3개를 3.5에 적었다. 내가 직접 밟은 것들이다** — 첫 조각 위치 추정 금지,
   짧은 숫자 조각의 토큰 경계 확인, 인용문이 선언을 품는 경우.
8. `is_reference_number`가 항목번호를 **대조 대상에서만 빼고 근거에서는 안 빼는** 비대칭이
   id 117 미탐의 직접 원인이다 (4.2). 근거 쪽에서도 빼는 것을 검토할 것.
9. `revalidate_summaries` 재측정 시 **줄어든 건수와 새로 생긴 건수를 함께** 보고할 것.

**ai-prompt**
1. 파생 수치 계산 금지 지시는 **불필요하다** — 계산은 일어나지 않았다 (5.1).
2. 실제로 필요한 지시는 **"본문에 쓴 모든 수치는 그 수치가 적힌 행을 인용하라"** (D 15토큰/10요약).
3. 단위 환산 금지 지시는 유효하다 — 진짜 오류 7토큰이 전부 환산에서 났다.
   다만 같은 모델이 id 110·123에서는 **같은 숫자를 정확히** 환산했다(1.1).
   **프롬프트만으로는 보장되지 않는다. 코드 환산이 본안이다.**
4. 인용 충실도 — P2 6건은 조사·어미·단어 치환이다. "원문을 한 글자도 바꾸지 말 것"을
   명시할 여지가 있다. P4(출력 오염)는 프롬프트로 못 고친다.
