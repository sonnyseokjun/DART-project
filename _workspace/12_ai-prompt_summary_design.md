### 1.3 선정: `gpt-5.6-luna`

1. **JSON 스키마 강제 지원** — 필수 조건. 실호출로 `strict: True` 스키마가 동작함을 확인했다.
2. **컨텍스트 1.05M** — 선정 시점에는 분기보고서 정제 후 약 219,807 토큰을 통짜로 넣는 것이
   전제였다. 이후 backend 섹션 추출로 최대 원문이 49,817 토큰까지 줄어(§8),
   **컨텍스트 크기는 더 이상 결정적 근거가 아니다.** 400K인 gpt-5.4-mini 로도 충분하다.
   그럼에도 luna 를 유지하는 이유는 3·4번이며, 향후 원문 규모가 커져도 상한에 닿지 않는다는
   여유는 계속 이점이다.
3. **최신 세대(2026-02 컷오프)** — 한국어 공시 용어·기업명 처리에 유리하다.
   다만 한국어 품질을 두 모델로 A/B 비교하지는 않았다. 실호출 3건에서 luna 의 한국어 요약이
   지침을 정확히 따랐다는 것까지만 확인했고, mini 대비 우위는 **미검증**이다.
4. **비용 차이가 작다** — 141건 실측 기준 luna $1.35 vs mini $1.01 로 **$0.34 차이**다(§7).
   이 규모에서는 세대 우위를 사는 편이 낫다.

`gpt-5.4-nano` 는 141건 $0.27 로 가장 싸지만, 중요도 판정·용어 풀이 품질을 검증하지 않았다.
**티어링(중요도 판정=nano, 해설=luna)은 공시당 호출 1회 원칙을 깨므로 채택하지 않았다.**

## 2. 출력 JSON 스키마

`DisclosureSummary` 모델 필드와 1:1 대응하고, 여기에 **원문 근거 배열(`evidence`)** 을 더했다.
코드상 단일 출처는 `summarizer.SUMMARY_JSON_SCHEMA` 이며 아래는 그 전문이다.

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["one_line", "easy_explanation", "why_important", "importance", "evidence"],
  "properties": {
    "one_line": {
      "type": "string",
      "maxLength": 200,
      "description": "공시 내용을 한 문장으로 압축한 요약. 200자 이내. 수치를 넣었다면 반드시 evidence에 원문 근거를 남긴다."
    },
    "easy_explanation": {
      "type": "string",
      "description": "회계를 모르는 일반인에게 설명하는 글. 3~5문장. 전문 용어는 첫 등장 시 괄호로 풀어 쓴다."
    },
    "why_important": {
      "type": "string",
      "description": "이 공시가 일반 투자자에게 어떤 의미를 갖는지. 1~3문장. 단정·전망·투자 권유 금지. 원문에 근거한 사실과 그 의미만 쓴다."
    },
    "importance": {
      "type": "string",
      "enum": ["high", "medium", "low"],
      "description": "중요도. high=주가에 직접 영향이 큰 사안(대규모 공급계약, 유상증자, 합병·분할, 대규모 투자·처분, 실적 급변, 소송·제재). medium=경영상 의미는 있으나 영향이 제한적인 사안. low=정기·형식적 보고나 소액 변동."
    },
    "evidence": {
      "type": "array",
      "minItems": 1,
      "maxItems": 8,
      "description": "요약에 등장한 모든 수치(금액·비율·주식수·날짜)와 핵심 주장의 원문 근거. 수치를 쓴 만큼 반드시 항목을 만든다.",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["field", "claim", "quote"],
        "properties": {
          "field": {
            "type": "string",
            "enum": ["one_line", "easy_explanation", "why_important"],
            "description": "이 근거가 뒷받침하는 요약 필드."
          },
          "claim": {
            "type": "string",
            "description": "요약문에 쓴 사실·수치를 그대로 옮긴 짧은 구절. 요약문에 없는 내용을 새로 쓰지 않는다."
          },
          "quote": {
            "type": "string",
            "description": "위 주장의 근거가 되는 원문 구절을 한 글자도 바꾸지 말고 그대로 복사한다. 요약·의역·재작성 금지. 200자 이내."
          }
        }
      }
    }
  }
}
```

### 설계 근거

- **`importance` enum 은 모델의 `Importance` choices 와 정확히 일치**한다(`high`/`medium`/`low`).
  스키마가 값을 강제하므로 저장 시 choices 위반이 나올 수 없다.
- **`one_line` 의 `maxLength: 200` 은 모델 `max_length=200` 과 동일하다.**
  실호출로 strict 모드가 `maxLength`·`minItems`·`maxItems` 를 거부하지 않음을 확인했다.
  다만 스키마 제약만 믿지 않고 `validate_summary()` 에서 파이썬으로 다시 길이를 검사한다(이중 제약).
  초과 시 하드 실패 → 재시도. 이 값이 넘으면 DB 저장이 깨지기 때문이다.
- `easy_explanation` 3~5문장은 **스키마 description + 시스템 프롬프트 + 프로그램 검사**의 삼중이지만,
  프로그램 검사는 **소프트(경고만)** 로 두었다. 문장 수는 저장을 깨뜨리지 않고,
  원문이 짧아 3문장이 안 나오는 것이 정상인 공시가 있어 하드 실패시키면 재시도만 낭비한다.
  실측 3건 모두 4문장으로 범위 안이었다.
- `strict: True` 규칙상 모든 프로퍼티가 `required` 이고 `additionalProperties: false` 여야 한다.

## 3. 시스템 프롬프트

`summary-standards` 의 프롬프트 필수 원칙 5개를 모두 반영했다.

| 스킬 원칙 | 반영 위치 |
|---|---|
| 1. 회계 비전공 일반인 대상, 용어 풀어쓰기 | §1 독자 (풀이 예시 3개 포함) |
| 2. 과장·투자 권유 금지 | §2 (금지 표현 12개를 명시적으로 열거) |
| 3. 불확실한 내용 단정 금지 | §3 |
| 4. 원문 인용 근거 | §4 + `evidence` 스키마 |
| 5. JSON 스키마 강제 | 프롬프트가 아니라 `response_format` 으로 강제 |

**가변 값(기업명·공시 제목·접수일자·접수번호·원문)은 시스템 프롬프트에 넣지 않았다.**
전부 `build_user_message()` 가 만드는 user 메시지로 간다. 시스템 프롬프트가 요청마다 동일한
접두사여야 프롬프트 캐시가 적중하기 때문이다.

전문 (`summarizer.SYSTEM_PROMPT`, 1,142 토큰):

```
너는 한국 금융감독원 전자공시(DART)에 올라온 기업 공시를 일반인이 이해할 수 있게
풀어 설명하는 요약 작성자다. 아래 원칙을 예외 없이 지켜라.

## 1. 독자
회계와 재무제표를 배운 적 없는 일반인이다. 주식을 처음 사 보는 직장인이라고 생각하라.
- 전문 용어는 첫 등장 시 반드시 괄호로 풀어 쓴다.
  예: "유상증자(회사가 새 주식을 찍어 팔아 돈을 마련하는 것)",
      "전환사채(나중에 주식으로 바꿀 수 있는 빚문서)",
      "자기주식 취득(회사가 자기 회사 주식을 사들이는 것)".
- 금액은 읽기 쉬운 단위로 환산해 병기한다. 예: "1,500억 원(약 1조 원의 15%)".
- 한 문장은 짧게 쓴다. 문어체 종결어미(~다)를 쓰고, 존댓말·구어체는 쓰지 않는다.

## 2. 과장·투자 권유 절대 금지
너는 투자 자문을 하지 않는다. 사실과 그 의미만 전달한다.
- 금지 표현: "호재", "악재", "매수 기회", "매도 시점", "주가 상승이 기대된다",
  "긍정적 신호", "실적 개선이 예상된다", "저평가", "성장 동력 확보", "수혜",
  "주목할 만하다", "관심을 가질 필요가 있다".
- 주가·실적의 방향을 예측하거나 암시하지 않는다.
- 좋고 나쁨을 평가하지 않는다. "이 계약은 회사 연매출의 12%에 해당한다"는 되지만
  "이 계약은 회사에 큰 도움이 된다"는 안 된다.

## 3. 불확실한 내용을 단정하지 않는다
- 원문에 없는 사실·수치·배경·전망을 만들어 내지 않는다. 아는 지식으로 보충하지 않는다.
- 원문에 없으면 쓰지 않는다. 빈칸을 추측으로 채우지 말고 그냥 언급하지 않는다.
- 원문이 조건부·잠정이면 그 사실을 그대로 옮긴다.
  예: "이사회에서 결정했으며 주주총회 승인이 남아 있다", "잠정 수치다".
- 원문 정보가 부족해 설명이 짧아지는 것은 정상이다. 억지로 늘리지 마라.

## 4. 모든 수치·핵심 주장에 원문 근거를 붙인다
요약에 쓴 금액·비율·주식수·날짜·기간은 하나도 빠짐없이 evidence 배열에 근거를 남긴다.
- quote 에는 원문 구절을 **한 글자도 바꾸지 말고 그대로 복사**한다.
  숫자의 쉼표·단위·띄어쓰기까지 원문 그대로여야 한다. 요약·의역·재작성은 위반이다.
- 원문에서 그대로 옮길 구절을 찾지 못했다면, 그 수치는 요약에 쓰지 마라.
- claim 에는 요약문에 실제로 쓴 표현을 그대로 옮긴다. 요약문에 없는 내용을 넣지 않는다.
- 근거는 요약문에 등장한 순서대로 담는다.

## 5. 중요도 판정
- high: 주가에 직접 영향이 큰 사안. 대규모 단일판매·공급계약, 유상증자·전환사채 발행,
  합병·분할·영업양수도, 대규모 시설투자·자산 처분, 실적의 급격한 변동,
  중대한 소송·행정제재, 최대주주 변경, 상장폐지·관리종목 관련.
- medium: 경영상 의미는 있으나 영향이 제한적인 사안. 소규모 계약, 자기주식 취득·처분,
  임원 변동, 정관 변경, 계열사 간 통상적 거래.
- low: 정기·형식적 보고, 소액 지분 변동, 정정 사항이 사소한 기재정정.
- 애매하면 낮은 쪽을 고른다. 중요도를 부풀리지 않는다.

## 형식
- 모든 출력은 한국어로 쓴다.
- one_line 은 200자 이내의 한 문장이다.
- easy_explanation 은 3문장 이상 5문장 이하다.
- why_important 는 1~3문장이며, 사실이 갖는 의미만 쓴다. 행동을 권하지 않는다.
- 마크다운 서식(**, #, - 등)을 쓰지 않는다. 평문으로 쓴다.
- 군더더기 표현을 붙이지 않는다. "공시 원문상", "원문에 따르면", "본 공시는",
  "이번 공시에서는" 같은 말머리 없이 곧바로 사실부터 쓴다. 근거는 evidence 로만 남긴다.
- 기업명은 공시 정보에 주어진 이름을 그대로 쓴다.
```

user 메시지 형식:

```

[공시 정보]
기업명: {company_name}
공시 제목: {report_name}
접수일자: {filed_at}
접수번호: {rcept_no}
공시 유형: {disclosure_type}

[공시 원문]
{raw_text}
```

| v1 (확정) | "형식"에 군더더기 말머리 금지 2줄 추가 | 스모크 1에서 요약문이 "공시 원문상 SK하이닉스가…"로 시작. 원칙 4(근거 요구)를 본문 말머리로 오해한 결과. 스모크 2·3에서 재발하지 않음 |

재현성 기록이 함께 따라간다.

## 4. 인용 근거 구조와 QA 대조 방법

### 왜 이 구조인가

`evidence[]` 의 각 항목은 `(field, claim, quote)` 3요소다.
- `quote` = **원문에서 한 글자도 바꾸지 않고 복사한 구절**
- `claim` = **요약문에 실제로 쓴 표현**

이렇게 두면 QA가 사람 판단 없이 두 단계로 기계 대조할 수 있다.

### 자동 대조 (코드로 이미 수행, 결과가 반환 dict에 담김)

| 판정 | 위치 | 의미 |
|---|---|---|
| `quote_found` | evidence 항목별 | `quote` 가 전처리 원문에 그대로(공백 정규화 후) 존재하는가. **False = 인용 자체를 지어냄** |
| `numbers_ok` / `missing_numbers` | evidence 항목별 | `claim` 의 수치가 `quote` 안에 있는가 |
| **`unsupported_numbers`** | 요약 전체 | **요약 본문(3필드)에 등장한 수치 중 어떤 인용문으로도 뒷받침되지 않는 값.** QA 숫자 대조의 본 관문 |

`unsupported_numbers` 가 항목별 판정보다 중요하다. 근거 하나가 주장 여러 개를 걸치면
항목별 `numbers_ok` 는 오탐이 나지만, 집계 검사는 "인용 없이 등장한 수치"만 정확히 걸러낸다.
실제로 스모크 2에서 요약이 쓴 `0.019%`(발행주식총수 대비)에 대응하는 `evidence` 항목이 없다는 것을
이 검사가 잡아냈다.

### 표 셀 구분자 처리 (backend 전처리와의 접점)

전처리된 원문은 표를 `합 계 | 80,948 | | 17,236,792,300` 형태로 담는다.
모델은 이를 `합 계 80,948` 처럼 구분자 없이 인용하는 일이 많아, 구분자를 그대로 두면
**정확한 인용인데도 `quote_found=False`** 가 된다.
`_normalize()` 가 구분자를 **공백으로 치환**해 이를 흡수한다. 통째로 지우지 않는 이유는
빈 셀을 사이에 둔 숫자가 `80,94817,236,792,300` 으로 붙어 버려 수치 대조가 더 나빠지기 때문이다.

검증 (합성 원문 `합 계 | 80,948 | | 17,236,792,300`):

| 인용 형태 | `quote_found` |
|---|---|
| `합 계 80,948` (구분자 없이) | True |
| `합 계 \| 80,948 \| \| 17,236,792,300` (그대로) | True |
| 줄바꿈만 다름 | True |
| `합 계 99,999` (원문에 없음) | **False** (진짜 오류는 계속 검출) |

빈 셀을 사이에 둔 값도 `80,948` / `17,236,792,300` 두 값으로 정상 분리된다.

수치 대조는 **자릿수 문자열이 아니라 값으로** 비교한다(`extract_numbers()`).
프롬프트가 `7,093,100,000,000원` → `약 7조 931억 원` 환산을 요구하므로 문자열 비교는 전부 오탐이 된다.
- 한국어 복합 단위(`7조 931억`)를 하나의 값 7,093,100,000,000 으로 합산해 파싱한다.
- 앞뒤가 영문자인 숫자(`P&T7`, `Fab2`)는 식별자로 보고 대조 대상에서 제외한다.
- `약`·`가량`·`여` 같은 근사 표현이 있으면 상대오차 5%까지 허용한다(`APPROX_TOLERANCE`).

오탐 제거 전후 (스모크 1 데이터로 검증):

| 케이스 | 수정 전 | 수정 후 |
|---|---|---|
| `약 7조 931억 원` vs 원문 `7,093,100,000,000` | 오탐(불일치) | 일치 |
| `청주 P&T7 생산시설` | 오탐(`7` 누락) | 대조 제외 |
| `자기자본 대비 5.88%` | 일치 | 일치 |
| `투자금액은 8조 원이다` (일부러 틀린 값) | 검출 | **검출** (오탐 제거 후에도 진짜 오류는 잡힘) |

### QA가 사람 눈으로 볼 항목

자동 대조가 통과해도 다음은 사람이 본다.
1. **금지 표현** — 프롬프트 §2 목록에 없는 우회 표현("기대", "전망", "긍정적")
2. **인용의 적절성** — `quote_found=True` 여도 그 인용이 `claim` 을 실제로 뒷받침하는지
3. **중요도 타당성** — high/medium/low 판정이 §5 기준에 맞는지
4. 중요도 `high` 는 `is_reviewed=False` 로 저장 → Django admin 검수 게이트

## 5. 프롬프트 캐싱

### 적용 방식

1. 시스템 프롬프트에 가변 값을 넣지 않아 **모든 요청의 접두사가 동일**하다.
2. `prompt_cache_key='dart-summary-{PROMPT_VERSION}'` 를 보낸다.
   공식 캐싱 문서가 GPT-5.6 이상에서 적중률 향상을 위해 권고하는 파라미터다.
3. 원문·메타데이터는 전부 user 메시지 뒤쪽에 둔다.

### 실측 결과

| 호출 | cached_tokens | cache_write_tokens | 입력 토큰 |
|---|---|---|---|
| 스모크 1 (거래소공시) | 0 | 2,963 | 2,966 |
| 스모크 2 (주요사항보고) | 0 | 4,278 | 4,281 |
| 스모크 3 (공정위공시) | **2,518** | 445 | 2,966 |

- 스모크 2가 미적중인 이유: 스모크 1과 2 사이에 프롬프트를 고쳤다(접두사 변경 → 캐시 무효화).
  **프롬프트를 고치면 캐시가 리셋된다는 것이 실측으로 확인된 셈이다.**
- 스모크 3은 스모크 2와 동일 접두사 → **2,518 토큰 적중**. 입력의 85%다.
- 캐시 적중분은 $1.00 → $0.10 으로 90% 할인된다.
- `cache_write_tokens` 는 GPT-5.6 계열에서 입력가의 1.25배로 청구된다(공식 캐싱 문서).
  코드의 `estimate_cost()` 가 이 배수를 반영한다.

### 중요: 정적 접두사가 2,542 토큰이라는 발견

캐싱 최소 임계는 1,024 토큰이다. 시스템 프롬프트만 세면 1,142 토큰으로 **아슬아슬하게** 넘는다.
그런데 실측 청구 입력 토큰이 tiktoken 추정보다 **원문 길이와 무관하게 일정하게 약 1,400 토큰 많았다**
(3건에서 각각 1402 / 1401 / 1404). JSON 스키마와 채팅 템플릿이 입력 토큰으로 함께 청구되기 때문이다.

따라서 실제 정적 접두사 = 1,142(프롬프트) + 1,400(스키마·템플릿) ≈ **2,542 토큰**이고,
이는 스모크 3의 실측 적중값 2,518 과 거의 일치한다.

이 상수를 `FIXED_PREFIX_OVERHEAD_TOKENS = 1400` 으로 코드에 반영했다. 반영 후 추정 정확도:

| 공시 | 추정 입력 토큰 | 실제 청구 | 오차 |
|---|---|---|---|
| 거래소공시 | 2,978 | 2,966 | +12 |
| 주요사항보고 | 4,216 | 4,281 | −65 |
| 공정위공시 | 2,898 | 2,966 | −68 |

**시스템 프롬프트를 1,024 토큰 아래로 줄여도 캐싱은 유지된다**(스키마가 접두사에 포함되므로).
다만 스키마를 크게 줄이면 상수를 다시 재야 한다.

### 생성된 요약 전문

#### 스모크 1 — SK하이닉스 신규시설투자등 (importance: high)

- **one_line**: 공시 원문상 SK하이닉스가 청주 P&T7 생산시설 건설에 약 7조 931억 원을 투자하며, 투자기간은 2025년 11월 26일부터 2032년 12월 31일까지다.
- **easy_explanation**: 공시 원문상 SK하이닉스가 청주 P&T7 생산시설을 새로 짓는 투자다. 투자금액은 7,093,100,000,000원(약 7조 931억 원)이며, 자기자본 대비 5.88%다. 투자기간은 2025년 11월 26일부터 2032년 12월 31일까지로 기재됐지만, 투자금액과 종료일은 향후 바뀔 수 있다. 회사는 생산 증가 대응과 클린룸 개장 일정 단축에 따라 건설 투자금액을 증액하기로 이사회에서 결정했다.
- **why_important**: 청주 P&T7 건설 투자금액은 자기자본 대비 5.88%다. 투자금액과 종료일은 향후 추진 과정에서 변동될 수 있다.
- evidence 8건. 원문 대조 결과 8건 모두 `quote_found=True`.
- **결함**: "공시 원문상" 말머리 → 프롬프트 수정으로 해결(§3).

#### 스모크 2 — 삼성전자 자기주식처분결정 (importance: medium)

- **one_line**: 삼성전자는 임원 등 928명에게 장기성과급 일부로 자기주식 보통주식 1,132,477주를 322,755,945,000원(약 3,228억 원)에 지급한다.
- **easy_explanation**: 삼성전자는 임원 등 928명에게 장기성과급(장기간의 성과를 기준으로 지급하는 보상)의 일부로 자기주식(회사가 보유한 자기 회사 주식) 보통주식 1,132,477주를 지급한다. 주당 가격은 285,000원이며, 처분예정금액은 322,755,945,000원(약 3,228억 원)이다. 주식은 2026년 7월 13일 회사의 자기주식 계좌에서 대상자의 개인별 계좌로 넘어갈 예정이다. 실제 처분 주식수와 금액은 지급 시점의 대상자 수와 주가에 따라 이사회 승인 한도 안에서 바뀔 수 있다.
- **why_important**: 회사가 보유한 자기주식을 임원 등에게 성과급으로 지급하는 거래다. 처분 예정 주식은 발행주식총수의 0.019% 수준으로 기재됐다. 실제 주식수와 처분금액은 지급 시점의 대상자 수와 주가에 따라 변동될 수 있다.
- **결함 1**: `0.019%` 에 대응하는 evidence 항목이 없다 → `unsupported_numbers` 로 검출.
  원문에 있는 값일 가능성이 높지만 **인용 없이 등장한 수치**이므로 QA 확인 대상이다.
- **결함 2**: evidence 1건의 `quote` 에 `||||` 구분자가 섞여 `quote_found=False`.
  모델이 원문을 그대로 복사하지 않고 표 구분자를 삽입했다. 인용 충실도 검사가 정상 작동한 사례다.
- 용어 풀이(`장기성과급`, `자기주식`) 지침을 정확히 따랐다.

#### 스모크 3 — SK하이닉스 특수관계인과의내부거래 (importance: medium)

- **one_line**: SK하이닉스가 계열회사인 에스케이텔레콤(주)과 업무용 항공기 공동관리 계약을 체결하며 거래금액은 122억 4,000만 원이다.
- **easy_explanation**: SK하이닉스는 계열회사인 에스케이텔레콤(주)과 2026년 업무용 항공기 공동관리 계약을 맺는다. 거래기간은 2026년 1월 1일부터 2026년 12월 31일까지다. 거래금액은 122억 4,000만 원이다. 이 계약은 SK 계열사들이 공동으로 구매해 운항 중인 업무용 항공기의 관리비와 운영비를 나누기 위한 것이다.
- **why_important**: SK하이닉스와 계열회사 사이의 업무용 항공기 관리 및 운영비 분담 거래다. 거래금액은 122억 4,000만 원이며, 이사회 의결을 거쳤다.
- **결함(중요)**: 원문은 `(단위 : 백만 원)` 아래 거래금액 `12,240` 이다. 즉 **122억 4,000만 원이 맞다** —
  모델의 단위 환산은 정확했다. 그러나 `quote` 를 `"(단위 : 백만 원)\n...\n라. 거래금액\n12,240"` 처럼
  **`...` 로 줄여 인용**해 `quote_found=False` 가 됐고, `122억 4,000만`(=1.224e10)과
  `12,240`(=1.224e4)의 값이 10^6 만큼 달라 `unsupported_numbers` 에 걸렸다.
- **평가**: 요약 자체는 정확하다. 검출된 것은 (a) 인용문 축약, (b) **단위 환산이 걸린 수치는 값 대조로
  자동 판정할 수 없다**는 한계다. `(단위 : 백만 원)` 같은 표 헤더 환산은 QA가 사람 눈으로 봐야 한다.
  이 케이스가 자동 대조의 경계를 정확히 보여준다.

### 종합 평가 (summary-standards 품질 기준)

| 기준 | 1 | 2 | 3 |

| 숫자 대조 (원문과 일치) | 통과 | 통과 | 통과 (환산 포함 정확) |

| 중요도 타당성 | 타당 (7조 시설투자) | 타당 | 타당 |
| 인용 충실도 | 8/8 | 7/8 | 3/5 |

숫자 정확성·금지 표현·할루시네이션은 3건 모두 통과했다. 남은 문제는 전부 **인용문 축약·변형**이며,
요약 본문의 정확성 문제가 아니다. 인용 충실도를 더 끌어올리려면 프롬프트 §4에
"인용문에 `...`, `[중략]` 등 생략 표기를 쓰지 말고 연속된 한 구절만 담아라"를 추가하는 것이 다음 개선안이다.
스모크 예산을 다 써서 이번에는 반영하지 않았다.

## 8. 정기공시 20만 토큰 처리에 대한 의견

> **해결됨 (2026-07-27)**: backend-pipeline이 아래 권고대로 규칙 기반 섹션 추출을 구현했다.
> 분기보고서 `20260514000391` 기준 246,375 → **7,756토큰 (96.9% 감소)** 로, 권고했던
> 2만~3만 토큰 목표보다 더 줄었다. 재무제표 **주석**(원문의 55%)·임원 명부·상세표를 버리고
> 사업의 개요·주요 제품·매출 및 수주상황·요약재무정보·배당·경영진단을 남겼다.
> LLM을 쓰지 않는 제목 접두어 화이트리스트라 공시당 1회 원칙도 유지된다.
>
> **섹션 구성 조정 (리더 지시)**: 이후 우선순위가 `III. 재무에 관한 사항` → `II.` 매출·수주 →
> 주요 제품·원재료 순으로 조정되어, `I. 회사의 개요` 를 빼고 **`II-3. 원재료 및 생산설비` 를 포함**한다.
> 정기공시 건당 5,839 → **7,757토큰**. 삼성전자 분기보고서 `20260515002181` 실측으로는
> 원재료 포함 11,424토큰 / 제외 7,530토큰이다.
> 비용 영향은 정기공시 11건 기준 $0.126 vs $0.083(차이 $0.043, 총액의 3%)로,
> **비용을 근거로 되돌릴 사안이 아니다.** 반도체 업종은 원가 구조·설비 투자가 실적 해석에
> 실질적이므로 요약 품질에 유리한 쪽이 맞다. 최대 원문(11,424+접두사=13,966토큰)도
> 상한 300,000의 5%에 불과하다.
>
> **추가 발견 (backend)**: 증권신고서가 분기보고서보다 컸다. `20260624000511`(SK하이닉스
> 유상증자)이 전체 정제 시 **413,650토큰**으로, 그대로였다면 `MAX_INPUT_TOKENS=300,000` 에 걸려
> `SummaryTooLargeError` 가 났을 것이다. 제2부가 사업보고서를 통째로 반복하는 구조라
> 제1부만 남겨 46,273토큰(88.8% 감소)으로 줄였다. **상한이 실제로 방어 장치로 작동한 사례**다.
>
> 현재 확보 15건 중 최대 원문은 49,817토큰이며, 접두사를 더해도 52,359토큰으로 상한의 17%다.
> 아래 본문은 섹션 추출 도입 **전** 판단 근거를 기록으로 남긴 것이다.

**결론: 통짜로 넣어도 동작하고 비용도 감당 가능하다. 그러나 섹션 추출을 권한다 — 비용이 아니라 품질 때문이다.**

1. **컨텍스트에 들어가는가 — 들어간다.**
   분기보고서 219,807 + 정적 접두사 2,542 ≈ 222,349 토큰. gpt-5.6-luna 컨텍스트 1,050,000 의 21%다.
   400K인 gpt-5.4-mini 로도 들어간다.
   `MAX_INPUT_TOKENS = 300,000` 으로 상한을 두어 이보다 큰 원문은 호출 없이 `SummaryTooLargeError` 를 던진다.

2. **비용 — 1건당 약 $0.22, 11건 $2.46.**
   금액 자체는 작다. 다만 전체 예산의 79%를 11건이 쓰는 구조이며,
   추적 기업이 늘거나 분기가 반복되면 이 비율대로 커진다.

3. **장문 요금 가산 — 미확인.**
   검색 결과에 "GPT-5.5는 272K 초과 입력 시 2배 가산"이라는 3자 출처 언급이 있었으나
   **공식 문서에서 확인하지 못했다.** 우리 최대치가 222K로 272K 아래라 당장 문제는 없지만,
   전처리가 부실해 30만 토큰을 넘기면 단가 체계가 달라질 수 있다. 확인 필요 항목으로 남긴다.

4. **진짜 문제는 품질이다.**
   분기보고서 220,000 토큰을 넣고 "3~5문장 쉬운 설명"을 받으면, 모델이 무엇을 고를지 통제할 수 없다.
   회사 개요·주주 현황·임원 명단 같은 상용구가 본문의 대부분인데, 요약 가치는
   **재무제표 요약·매출 구성·주요 변동 사항**에 몰려 있다. 입력이 길수록 핵심이 묻힌다.
   스모크 테스트는 짧은 공시 3건뿐이라 이 위험을 실증하지는 못했다 — 판단 근거는 원문 구조다.

5. **권고**
   - 정기공시는 backend 전처리에서 **핵심 섹션만 추출**한다. 우선순위:
     `II. 사업의 내용` 중 매출·수주 현황 → `III. 재무에 관한 사항`(요약재무정보) →
     `II. 사업의 내용` 중 주요 제품·원재료. 회사 개요·주주·임원·계열회사 현황은 버린다.
   - 목표 2만~3만 토큰. 달성 시 정기공시 1건 $0.22 → 약 $0.03, 11건 $2.46 → 약 $0.36.
     **전체 136건이 $3.10 → 약 $1.00 이 된다.**
   - 섹션 추출을 **요약과 별도 단계**로 두고 추출 결과를 눈으로 확인한 뒤 요약을 돌린다.
     LLM으로 섹션을 고르는 방식은 공시당 호출 1회 원칙을 깨므로 쓰지 않는다. 규칙(제목 정규식) 기반이어야 한다.
   - 섹션 추출 전에는 **정기공시 요약을 실행하지 않기를 권한다.** 일반 공시 125건($0.65)을
     먼저 돌려 품질을 확인하는 것이 순서상 안전하다.

## 9. `models.py` 변경 제안

모델 파일은 수정하지 않았다(파일 소유권 준수). 아래는 제안이다.

### 제안 1 (권장) — `DisclosureSummary.evidence` JSONField 추가

```python
evidence = models.JSONField('원문 근거', default=list, blank=True)
```

- **필요한 이유**: 지금 `summarize_disclosure()` 가 반환하는 `evidence` 는 저장할 곳이 없어 버려진다.
  근거를 버리면 (a) QA가 재검증할 때마다 LLM을 다시 호출해야 하고 — 공시당 1회 원칙 위반 —
  (b) 사후에 요약 오류가 발견돼도 어느 원문 구절에서 왔는지 추적할 수 없다.
- `verify_evidence()` 판정(`quote_found`, `numbers_ok`)까지 함께 담으면 admin 검수 화면에서
  의심 항목을 바로 보여줄 수 있다.
- SQLite도 Django 5.2 JSONField를 지원한다.

### 제안 2 (권장) — `DisclosureSummary.needs_review` 또는 경고 저장

```python
review_warnings = models.JSONField('자동 검증 경고', default=list, blank=True)
```

- `unsupported_numbers` 가 비어 있지 않은 요약은 중요도와 무관하게 사람이 봐야 한다.
  현재 `is_reviewed` 만으로는 "검수 안 함"과 "검수 필요"를 구분할 수 없다.
- 대안: 필드를 늘리지 않고 `is_reviewed=False` + 경고를 `evidence` JSON 안에 함께 넣는 방법도 있다.

### 제안 3 (선택) — `model_name` `max_length` 확대

- 현재 50. `gpt-5.6-luna`(12자)는 여유롭지만, 날짜 스냅샷 ID(`gpt-5.4-mini-2026-03-17`, 23자)도 안전하다.
  당장 문제는 없다. 코드에서 `model_id[:50]` 으로 자르고 있으므로 **변경하지 않아도 된다**.

### 제안 4 (선택) — 토큰·비용 기록

- 비용 추적을 DB에서 하려면 `input_tokens`/`output_tokens`/`cached_tokens` 정수 필드가 필요하다.
  당장은 관리 명령 로그로 충분하다고 보아 **후순위**로 둔다.

| 30 | `SYSTEM_PROMPT` | 가변 값 미포함 | 프롬프트에 `{`·`%s`·`format` 자리표시자가 없음 |
| 31 | 〃 | 캐싱 임계 | `static_prefix_tokens() >= 1024` |
| 32 | `SUMMARY_JSON_SCHEMA` | 모델 정합성 | `importance` enum == `DisclosureSummary.Importance.values` |
| 33 | 〃 | 〃 | `one_line.maxLength` == `DisclosureSummary._meta.get_field('one_line').max_length` |
| 34 | 〃 | strict 규칙 | 모든 object에 `additionalProperties=False`, `required` == `properties` 키 전체 |

32·33은 스키마와 모델이 어긋나면 즉시 깨지는 회귀 방지 테스트다. 반드시 넣기를 권한다.

### backend 연동 시 알아둘 것

- `summarize_disclosure()` 는 **전처리를 하지 않는다.** `raw_text` 는 정제가 끝난 원문이어야 한다.
- 반환 dict의 `one_line`/`easy_explanation`/`why_important`/`importance`/`model_name` 을 그대로 모델에 넣으면 된다.
- `importance == 'high'` 이면 `is_reviewed=False` 로 저장한다(검수 게이트).
- `evidence`·`unsupported_numbers`·`warnings` 는 저장할 곳이 없다 → §9 제안 참조. 최소한 로그에 남겨야 한다.
- 모든 예외가 `SummarizerError` 하위다. 이것만 잡으면 건별 실패 처리가 된다.
- 호출 전 `Disclosure.summary` 존재 여부를 반드시 확인한다(공시당 1회 원칙).

## 12. 미해결·확인 필요

1. **`.env` 의 `OPENAI_API_KEY` 에 공백이 섞여 있다.** 그대로 쓰면 401이 난다.
   `_get_client()` 에서 공백을 제거해 우회했고 실호출은 정상이지만, `.env` 원본을 고치는 편이 낫다
   (`.env` 는 내 소유 파일이 아니라 수정하지 않았다).
2. 장문 입력(272K 초과) 요금 가산 여부 — **공식 문서 미확인**.
3. `gpt-5.4-nano` 의 컨텍스트·Structured Outputs 지원 — **미확인**.
4. 한국어 품질의 모델 간 비교(luna vs mini) — **미검증**. 스모크 예산상 luna만 확인했다.
5. ~~지분공시·발행공시의 실제 토큰 수~~ — **해소.** backend 실측(141건 715,508토큰)으로 §7 갱신.
6. 인용문 축약(`...`) 금지 규칙 — 다음 프롬프트 개선안. 이번에는 미반영.
   섹션 추출로 원문이 짧아져 모델이 인용을 줄여 쓸 유인도 줄었을 가능성이 있으나 **미검증**이다.
7. 표 구분자 대조는 합성 원문으로만 검증했다. 실제 정기공시 요약에서 표 인용이
   어떻게 나오는지는 **실호출로 확인하지 않았다**(스모크 3건은 모두 짧은 공시).
   대량 실행 시 정기공시 첫 1건의 `quote_found` 비율을 먼저 확인하기를 권한다.
